# Deploying Vanguardia Financial

Everything deploys from `render.yaml` as one Render Blueprint: API, Postgres,
Redis, and the frontend as a static site.

## Why Render and not Vercel

The API starts a background engine at boot (`lifespan` in `backend/app/main.py`)
that polls prices, enforces margin stop-outs and writes equity snapshots on a
timer. Vercel's Python runtime is serverless — a function runs per request and
exits — so that loop would never run. Prices would freeze and a losing account
would never be stopped out. `vercel.json` was removed for this reason.

The frontend has no such constraint. It is a static export and can be hosted
anywhere; Render keeps it beside the API, but Vercel or Cloudflare Pages work
equally well if you prefer.

## Before you start

- [ ] Code pushed to GitHub
- [ ] A Render account
- [ ] DNS control for `vanguardiafinancial.com`
- [ ] Real deposit wallet addresses (BTC is set; USDT, TRX and USD are still
      placeholders and will take deposits nowhere)

## 1. Create the Blueprint

Render Dashboard → **New** → **Blueprint** → pick the repo. It reads
`render.yaml` and creates all four services.

`SECRET_KEY` is generated by Render. `TWELVEDATA_API_KEY` is marked
`sync: false`, so it is left blank for you to fill in later — blank is fine,
prices then come from CoinGecko and Yahoo as they do in development.

## 2. Point DNS at it

In the frontend service → **Settings** → **Custom Domain**, add
`vanguardiafinancial.com` and `www.vanguardiafinancial.com`. Add the API as
`api.vanguardiafinancial.com` on the backend service. Then create the CNAME
records Render shows you.

The URLs in `render.yaml` assume exactly this split:

| Host | Service |
|---|---|
| `vanguardiafinancial.com` | frontend |
| `api.vanguardiafinancial.com` | backend |

If you use different hostnames, update `CORS_ORIGINS`,
`NEXT_PUBLIC_API_BASE_URL` and `NEXT_PUBLIC_SITE_URL` to match. A mismatch in
`CORS_ORIGINS` blocks every request from your own frontend, and it is the most
common reason a fresh deploy shows a working site that cannot log in.

## 3. Migrations

`preDeployCommand` runs `alembic upgrade head` on every deploy, so the schema
is never behind the code. Nothing to do by hand.

## 4. Seed the asset catalogue

A new database has no instruments. From the backend service's **Shell**:

```bash
cd backend
python -m scripts.seed                 # demo users and the original assets
python -m scripts.seed_universe        # the full 385-instrument catalogue
python -m scripts.seed_deposit_wallets # deposit methods
```

`seed_universe` is idempotent — re-running it patches rather than duplicates.

## 5. Set the real deposit addresses

`seed_deposit_wallets` inserts placeholders. It only creates rows that do not
exist, so editing the script later changes nothing. Update the database:

```sql
UPDATE deposit_wallets SET wallet_address = '<address>', updated_at = now()
 WHERE currency_symbol = 'USDT';
```

Verify each address by scanning the QR with your own wallet before anyone
sends to it. A wrong deposit address loses funds permanently.

## 6. Check it works

- `https://api.vanguardiafinancial.com/api/health` returns ok
- `https://api.vanguardiafinancial.com/api/v1/markets/status` reports
  `live_symbol_count` around 385
- The site loads, a user can register and log in
- Prices move — confirms the background engine is running and the service is
  not asleep

## Known gaps before real users

These are open regardless of hosting:

1. **Crypto deposits credit balances trading cannot reach.** Deposits credit an
   account in the deposit's currency; trading debits USD, with no conversion.
2. **`is_verified` is never enforced** — any account can switch to REAL and trade.
3. **Take-profit and stop-loss are recorded but never fire.** No trigger loop.
4. **Yahoo Finance is the price feed for non-crypto.** An undocumented endpoint
   whose terms do not permit commercial redistribution. Set
   `TWELVEDATA_API_KEY` before taking paying users.
5. **No test suite.**
